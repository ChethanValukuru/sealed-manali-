Safe AI security testing

Test an AI safely — and trust the result.

To check if an AI is safe, one team tries to trick it (the attackers) while another team defends it (the defenders). The catch: if they all share one space, they can peek at each other and the AI can get confused between tests — so the result can't be trusted. sealed keeps everyone in separate rooms, lets them work at the same time, and keeps a record no one can secretly change.

The simple idea

Think of testing a bank vault. You hire people to try to break in, and people to defend it. If the two groups can watch each other — or if someone can edit the security camera footage — the test proves nothing.

Separate rooms

The attackers, the defenders, and the AI each work in their own locked space. None can see or reach the others.

A trusted go-between

All messages pass through one honest middleman. It decides who is allowed to see what, and when.

Tamper-proof record

Every action is written down in a way that makes any later edit obvious — so the findings hold up.

What goes wrong without it

The defenders peek

If the defenders can see the attack before the test is over, they can quietly prepare for it — and the "pass" is fake.

The AI gets confused

If the AI remembers the last test, a trick from one test can carry over and spoil the next one.

Hidden leaks

Sharing the same machine opens subtle side-channels (timing, shared memory) that ordinary setups ignore.

How it works

Everything flows through one trusted go-between — the broker. There's no direct line between the teams, and every step is recorded.

Walls that hold

Each team is boxed in so it can't reach, see, or read any other team. (Done with separate networks, locked-down containers, and strict permissions.)

Results you can check yourself

The record is signed and chained together. Change one line and a quick check points to the exact spot — proof the findings are real. (A hash chain with digital signatures.)

A fresh AI every test

The AI starts each test with a blank memory, so nothing carries over from the last one.

Honest about limits

A side-by-side demo shows the leak happening, then shows it blocked — and the limits page says plainly what it doesn't cover.

What it sets out to do

  • 01Stay fast while staying safe
    The extra security doesn't slow the test down to a crawl — the overhead is measured, not guessed.
  • 02Stop information leaking
    Teams can't reach, watch, or read each other; the attack stays hidden from the defenders until the test ends.
  • 03Keep an honest record
    A tamper-proof log where any change is caught — and pointed to exactly.
  • 04Run anywhere normal
    Works on an ordinary cloud server with standard tools — no special hardware.
  • 05Handle AI-specific risks
    A fresh AI memory per test, so one test can't poison the next.
  • 06Be honest about the gaps
    The limits are written down as clearly as the protections.

What it protects — and what it doesn't

A security tool you can't trust about its own limits isn't worth much. So here's the honest version, in plain terms.

It stops these

  • Teams spying on each other's files, programs, or network
  • Defenders seeing the attack too early
  • One test's trick leaking into the next
  • Anyone secretly editing the record
  • A team calling something it isn't allowed to

It reduces these

  • Timing clues — smoothed out, but not perfectly erased
  • Shared-resource clues — limited per team, not fully removed

It doesn't claim these

  • Deep chip-level leaks on shared processors
  • A hacked server or operating system
  • A dishonest go-between (the broker is trusted here)

A few words, explained

Red team / attackers

People (or scripts) whose job is to try to break or trick the system.

Blue team / defenders

People (or tools) whose job is to catch and block those attacks.

Audit log

A running list of everything that happened — here, built so it can't be quietly changed.

Side-channel

An indirect leak — learning a secret from timing or shared resources instead of the data itself.
