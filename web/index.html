Secure adversarial AI testing

Isolate the attack, the defense, and the model — and prove it.

AI safety teams test a model by having a red team attack it and a blue team defend it. When all three share one sandbox, the attack can leak to the defenders, the defense to the attackers, and the model gets contaminated between tests. Every finding is then quietly worthless. sealed keeps the three sealed off while they run together, records every action in a tamper-evident log, and states exactly what it does and doesn't protect.

Why shared sandboxes break safety testing

Premature disclosure

The red team's attack payload becomes visible to the blue team before a test concludes — the result is rigged.

Context contamination

A shared model carries state across tests: one test's planted prompt bleeds into the next.

Cross-tenant leakage

Containers share a kernel, network and inference backend — opening side channels standard isolation ignores.

How it works

A broker mediates all traffic — there is no direct path between tenants. Every event is written to an append-only, cryptographically verifiable audit log.

Isolation that holds

Per-tenant networks (the broker is the only reachable peer), seccomp, dropped capabilities, read-only rootfs, and cgroup limits. No tenant can reach, see, or read another.

Findings you can verify

Every event is hash-chained and Ed25519-signed. Edit one entry and the verifier flags the exact break — safety findings become independently checkable.

Fresh model, every test

The model under test gets a clean context per test with no KV or conversation carryover, so one test cannot contaminate the next.

Honest by construction

A naive-vs-secure demo makes the leak visible, then contained; the threat model states plainly what remains out of scope.

What it sets out to do

  • 01Isolate without breaking function
    The sealed eval loop still runs in real time — overhead is measured, not assumed.
  • 02Prevent information leakage
    Network segmentation, container isolation, disclosure gating, timing normalization.
  • 03Guarantee audit integrity
    Hash-chained, signed, append-only log with a verifier that pinpoints tampering.
  • 04Build for deployability
    Runs on a stock Linux VM with standard runtimes — no special hardware.
  • 05Address LLM-native threats
    Fresh context per test; output isolation; no cross-session contamination.
  • 06Quantify residual risk
    An honest threat model — the limits are stated as plainly as the guarantees.

What it protects — and what it doesn't

A safety tool you can't trust about its own limits is worthless. So the limits are stated here, not buried.

In scope

  • Cross-tenant network, process and filesystem observation
  • Premature disclosure of red's payload to blue
  • Cross-session model contamination
  • Audit tampering (edit, insert, delete, reorder)
  • Unauthorized cross-role calls (capability tokens)

Partially mitigated

  • Timing side channels — normalized to a quantum, not eliminated
  • Resource-contention channels — cgroup-partitioned, not removed

Out of scope

  • CPU microarchitectural side channels on shared cores
  • A compromised host kernel or container engine
  • A malicious broker (it is trusted in this model)
